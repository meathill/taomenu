# TaoMenu 产品需求文档

- 文档状态：MVP 基线
- 版本：0.4
- 更新日期：2026-07-27
- 目标市场：越南中小餐饮门店

## 1. 产品定义

TaoMenu 是门店购买并自行运营的线下经营软件。顾客已经通过门店自身的位置、品牌或推广进入门店，TaoMenu 只为本次堂食或到店取餐提供菜单展示、扫码点单、订单同步、取餐叫号和人工结账记录。

TaoMenu 的核心价值不是为餐厅带来流量，而是：

1. 减少服务员往返记录和重复确认订单的时间。
2. 让顾客在语言不通时仍能自主查看菜单和下单。
3. 让多名员工在高峰期同时处理同一门店的订单。
4. 在不改造 POS、打印机和后厨硬件的前提下完成轻量数字化。
5. 让没有电脑的店主也能只用一部手机完成开店、建菜单和日常经营。
6. 让法棍、饮品和其他无座/少座小店可用取餐号处理外带订单，不强制虚构桌号。

### 1.1 业务边界

为保持“线下经营 SaaS”定位，产品必须长期遵循以下边界：

- 不提供餐厅发现、排名、推荐或跨店搜索。
- 不提供跨餐厅购物车、订单或消费者账号。
- 不参与餐厅与顾客之间的定价、成交、履约和争议处理。
- 不代收餐费，不保存商户余额，不做钱包、储值、会员预付费或提现。
- 餐厅是菜单、价格、订单接受、食品履约、收款和退款的唯一责任主体。
- TaoMenu 仅向餐厅收取软件订阅或技术服务费。
- 顾客页面明确显示餐厅身份；TaoMenu 只作为技术服务提供方出现。

这套边界是产品和合同设计前提，不替代上线地区的正式法律意见。

## 2. 问题与机会

### 2.1 门店问题

- 小店菜单不多，但缺少易用、低成本的数字点餐工具。
- 高峰时服务员需要在桌台、收银台和后厨之间反复沟通。
- 只有一台收银手机时，其他员工无法及时确认订单和结账。
- 法棍店、饮品店等无座/少座门店不适合“一桌一码”，高峰期需要简单可辨的取餐号和待叫号队列。
- 外国游客与本地员工之间存在语言障碍。
- 完整 POS、打印机和后厨系统成本高、部署重，不适合小店。

### 2.2 顾客问题

- 纸质菜单可能只有越南语，游客难以理解菜品。
- 等待服务员拿菜单、点单和结账的时间长。
- 口头点单容易因语言、发音或环境噪音产生错误。

### 2.3 产品机会

用顾客自己的手机完成菜单浏览和订单提交，用门店已有手机完成接单与结账记录，不要求商户采购硬件。免费版以完整手工流程消除首次尝试门槛，付费版通过多语言、多员工协作、拍照导入和越南语语音助手解决真实经营瓶颈。

## 3. 目标用户

### 3.1 决策者：店主或店长

- 经营 1～3 家小型餐厅、咖啡店、饮品店、法棍店或街边外带店。
- 使用智能手机和银行转账，但没有专职 IT 人员。
- 可能没有电脑、平板或 POS，所有店主任务都必须能在手机浏览器/PWA 中完成。
- 关心部署速度、员工学习成本和高峰期效率。
- 愿意为明确节省的人力和等待时间付费。

### 3.2 使用者：服务员或收银员

- 通过门店员工终端查看新订单、更新订单状态和记录结账。
- 需要极少的培训，操作必须适合忙碌和嘈杂环境。
- 多名员工可能同时操作同一桌订单。

### 3.3 最终使用者：到店顾客

- 扫描桌面二维码进入当前餐厅和桌台，或扫描柜台/门口的取餐码进入当前门店。
- 不应被要求下载 App 或注册账号。
- 需要快速加载、清晰菜单和明确的下单结果。

## 4. 产品目标与非目标

### 4.1 MVP 目标

- 店主只用一部手机，在 15 分钟内完成注册、菜单创建、经营模式选择和首张桌码或取餐码分享/打印。
- Pro 店主可拍摄现有纸质菜单，让 AI 生成结构化草稿并逐项确认，无需在手机上重新录入全部菜品。
- Pro 店主和员工可使用越南语语音输入与受控语音指令；Free 只提供触控和手工输入。
- 顾客在 30 秒内从扫码进入菜单并开始选菜。
- 顾客无账号即可提交订单，并获得可确认的订单编号和状态。
- 柜台取餐订单使用门店当日唯一的短取餐号；员工标记可取后口头叫号，顾客无需提供姓名或手机号。
- 顾客可在不注册的情况下“呼叫服务员”或“请求结账”，并由员工端确认处理。
- 免费门店可以用一个员工终端完整营业。
- 付费门店可以让多个员工终端实时看到一致订单状态。
- 已安装并授权通知的员工 PWA 在锁屏或退到后台时可以收到新订单 Push Notification。
- 门店可用现金或自己的转账二维码收款，TaoMenu 不接触餐费。
- 付费门店可以发布多语言菜单。

### 4.2 MVP 非目标

- 餐厅发现、外卖配送、预约和营销获客。
- 自动支付确认、代收、分账、退款和拒付处理。
- 原生 iOS/Android App。
- POS、打印机、钱箱和后厨硬件集成。
- 自动扬声器叫号、电子取餐大屏和短信取餐通知；MVP 由员工看手机大号码后口头叫号。
- 库存、采购、财务、税务发票和员工排班。
- 储值会员、优惠券、积分和跨店忠诚度体系。
- AI 自动发布、自动改价、面向顾客的菜品推荐或聊天机器人。
- 任何不经店主确认就对顾客生效的 AI 内容。
- 广告系统。

## 5. 核心概念

### 5.1 门店 Store

一个独立经营主体及其配置、员工终端、菜单、桌台和订单数据的租户边界。MVP 一个账号可以创建一个门店，多门店在后续版本提供。

#### 5.1.1 经营模式 Service Mode

门店可选择“桌边堂食”、“柜台取餐”或“混合模式”。该配置决定首次引导、员工工作台默认视图和可创建的二维码类型，但店主之后可随时切换为混合模式。

### 5.2 桌台 Table

餐厅内可复用的桌号或点单位置。每个桌台拥有长期二维码，二维码只定位门店和桌台，不包含顾客身份。

### 5.3 用餐批次 Table Session

从该桌第一笔订单开始，到员工完成结账并关闭桌台为止的一次用餐。多名顾客可从不同手机向同一个用餐批次追加订单。

### 5.4 取餐点 Pickup Point

门口、柜台或排队区可复用的公共扫码点。多位顾客可同时通过同一张取餐码创建互相独立的外带订单；这些订单不共享 table session，也不合并账单。

### 5.5 取餐号 Pickup Number

按门店当地营业日生成的短号码，例如 `A023`。取餐号可以公开叫号，但不是查看订单明细的密钥；顾客仍使用不可猜的 public token 查看自己的订单。

### 5.6 员工终端 Staff Terminal

被门店授权、可处理订单的浏览器或 PWA 实例。订阅限制的是同时活跃终端数，而不是历史登录设备总数。

### 5.7 订单与结账

订单描述顾客点了什么；结账记录描述门店确认收到了多少钱。二者状态独立，避免把“菜已上齐/餐已取走”和“已经付款”混为一谈。

## 6. 版本与商业模式

具体价格在试点后确定，MVP 先固化权益边界。公测阶段以 `149.000 ₫/月`、`1.490.000 ₫/年` 作为首个价格实验，年付相当于付 10 个月；该价格是待验证假设，不是已确定的长期定价。封闭试点仍以管理员手工授权 Pro 为主。

| 能力 | Free | Pro |
|---|---:|---:|
| 门店数 | 1 | 1 |
| 菜单分类、菜品、桌台和取餐点 | 不限 | 不限 |
| 顾客扫码和订单数 | 不限 | 不限 |
| 呼叫服务员/请求结账 | 支持 | 支持 |
| 手工创建和编辑菜单 | 支持 | 支持 |
| 拍照/PDF AI 建菜单 | 不支持 | 支持 |
| 可发布菜单语言 | 1 种 | 最多 5 种 |
| AI 翻译草稿 | 不支持 | 支持 |
| 越南语语音输入与指令 | 不支持 | 支持 |
| 同时活跃员工终端 | 1 台 | 最多 5 台 |
| 多终端实时同步 | 不适用 | 支持 |
| 订单和结账核心功能 | 支持 | 支持 |

商业原则：

- 不限制菜单数量，以免免费版对小店失去实用价值。
- 不以去品牌作为主要收费点。
- 顾客设备永远不计入员工终端额度。
- 免费版必须能完成真实营业闭环；付费版解决高峰期协作和多语言问题。
- Free 的菜单必须逐项手工录入；所有语音识别、图片/PDF 识别和 AI 翻译请求都由服务端 Pro 权益控制。
- Pro 的 AI 能力不改变人工审核要求，AI 生成内容和语音指令都不能绕过确认、权限和业务校验。
- 订阅由餐厅向 TaoMenu LLC 单独支付，与餐费完全分离。
- 月付和年付价格使用可配置产品数据，不写死在客户端；试验期将注册、首份菜单发布、首笔真实订单和续费作为判断依据。

## 7. 核心用户流程

### 7.1 店主首次启用

1. 店主在手机浏览器中使用 Google 账号快捷登录，或使用邮箱验证码注册并登录。
2. 创建门店，填写名称、默认语言、时区、币种，并选择桌边堂食、柜台取餐或混合模式。
3. Free 店主手工创建菜单；Pro 店主也可以直接用相机拍摄/上传现有菜单，由 AI 生成结构化草稿。
4. 在手机上校对分类、菜品、价格、规格和翻译，再发布菜单。
5. 堂食门店创建桌台码；取餐门店创建柜台/门口取餐码。通过系统分享面板发送二维码图片/PDF，或保存后交给附近打印店打印。
6. 在自己的手机上配对首个员工终端。
7. 扫描任意桌码或取餐码完成测试订单。
8. 确认测试成功后开始营业。

完成标准：门店至少有一个已发布菜单、一个可用的桌台或取餐点，以及一个已配对终端。

### 7.2 顾客扫码点单

1. 堂食顾客扫描桌码；外带顾客扫描柜台、门口或排队区的取餐码。
2. 页面显示门店名称以及桌号或“到店取餐”。
3. 顾客选择菜品、规格、数量并填写可选备注。
4. 提交前复核菜品、数量和总价。
5. 系统创建订单；堂食显示订单号，外带显示更大、更易叫号的当日取餐号。
6. 顾客无需停留在点餐页面。切回页面、从浏览器历史恢复或主动下拉刷新时，再从服务端获取最新订单状态。

约束：

- 不要求姓名、手机号、邮箱或消费者账号。
- 菜品售罄或价格变化时，提交接口必须以服务端最新数据复核。
- 重复点击或网络重试不能创建重复订单。

### 7.3 员工处理订单

1. 员工终端发出声音和视觉提示。
2. 新订单显示桌号或取餐号、订单号、菜品和备注。
3. 员工接受或取消订单。
4. 堂食订单完成后标记“已上菜”；外带订单做好后标记“可取餐”，叫号后标记“已取餐”。
5. 所有活跃员工终端实时看到相同状态。

MVP 订单状态：

- `submitted`：顾客已提交，等待门店处理。
- `accepted`：门店已接受。
- `served`：堂食订单已完成上菜。
- `ready_for_pickup`：外带订单已做好，等待员工叫号和顾客取走。
- `picked_up`：外带订单已由顾客取走。
- `cancelled`：门店取消，并记录原因。

### 7.4 外带取餐与员工叫号

1. 外带顾客扫描公共取餐码下单；顾客不愿扫码时，员工也可在员工端代建一笔外带订单。
2. 每笔订单独立生成当日取餐号，不创建 table session，也不与前后顾客合并账单。
3. 员工接单并制作；做好后点击“可取餐”，员工端用大字显示取餐号，供员工口头叫号。
4. 顾客通常会切换到其他应用；TaoMenu 不要求页面常驻、不在后台持续轮询，也不向取餐顾客申请 Push 通知权限。
5. 顾客切回订单页时，页面立即刷新状态；顾客也可主动下拉刷新。线下口头叫号是 MVP 的主要取餐提醒。
6. 员工交付餐品后点击“已取餐”；如需再叫一次，可使用“再次叫号”，但不改变付款状态。
7. 现金或转账由门店直接收取；员工可在订单上单独记录付款，不依赖桌台账单。

### 7.5 追加点单

同一桌台在当前用餐批次未关闭时，来自任意顾客设备的新订单自动归入该批次。员工端同时显示每笔订单和桌台累计金额。

### 7.6 呼叫服务员与请求结账

1. 堂食顾客在菜单或订单状态页打开“需要帮助”。公共取餐码不提供桌边服务请求。
2. 选择“呼叫服务员”或“请求结账”，页面再次显示餐厅和桌号。
3. 提交后顾客看到已发送、已确认或已完成状态，不需填写姓名或手机号。
4. 员工工作台以桌号和请求类型显示提醒，员工可“已响应”或“已完成”。
5. 同桌同类型只能存在一个未完成请求，重复点击返回当前状态，不重复轰炸员工端。

“请求结账”只表示顾客希望员工来结账，不是支付指令，不变更付款状态，也不代表 TaoMenu 处理资金。

### 7.7 人工结账

1. 员工打开桌台账单，查看所有未取消订单总额和已记录付款。
2. 顾客使用现金或直接向餐厅转账。
3. 员工选择付款方式并记录金额。
4. 应付余额为零后，员工关闭桌台。
5. 下一位顾客点单时创建新的用餐批次。

MVP 支持现金、银行转账和其他三种记录类型。付款记录是门店的人工确认，不代表 TaoMenu 处理或验证了资金。

### 7.8 员工终端配对

1. 店主在管理后台生成短时有效的配对码。
2. 员工设备输入配对码，获得当前门店的终端凭证。
3. 终端进入订单工作台并申请活跃席位。
4. 超过套餐并发上限时，提示升级或由店主停用旧终端。

本地 PIN 只用于解锁已经配对的终端，不能作为互联网上的独立身份凭证。

### 7.9 Pro：手机拍照建菜单与 AI 草稿

1. 店主用手机相机连续拍摄纸质菜单，或上传已有图片/PDF。
2. 系统识别分类、菜名、描述、价格和规格，生成结构化菜单草稿。
3. 无法确定的字段、高风险价格和低置信度文本必须醒目标记。
4. 店主逐页核对，也可以直接在手机上修改、删除、合并和调整顺序。
5. Pro 店主可选择目标语言并生成翻译草稿；订单端始终保留门店基础语言，方便员工识别。
6. 只有店主明确点击发布后，AI 草稿才会出现在顾客菜单中。

AI 首先解决“手机录入整份菜单太慢”这个激活问题。它不代替店主对菜名、价格、过敏原和翻译准确性的责任。

### 7.10 Pro：越南语语音输入与操作

1. 店主或员工主动按住语音按钮说出短指令，不持续监听环境。
2. 系统把越南语语音转写成文本，并结合当前门店菜名、桌号和常用词解析为结构化指令草稿。
3. 搜索、打开桌台等只读指令可以立即执行；新增/修改菜单、售罄、接单、取消、结账和关桌等写操作必须显示确认卡。
4. 用户核对桌号、菜品、数量、金额和动作后点击确认，服务端再按当前权限和业务状态执行。
5. 识别结果不确定、金额冲突或目标不存在时，只展示候选项，不执行任何写操作。

Free 用户点击语音入口时展示 Pro 说明和升级入口，不申请麦克风权限、不录音，也不创建 AI 任务。

## 8. 功能需求与验收标准

### 8.1 账号与门店

- 店主可通过 Google OAuth 或邮箱验证码登录；MVP 不接入短信验证码或 Zalo 登录。
- 门店保存名称、slug、时区、币种、默认语言和营业状态。
- 门店保存经营模式：桌边堂食、柜台取餐或混合模式；切换模式不删除历史订单。
- 所有后台数据访问必须验证当前用户与门店的成员关系。
- 删除门店必须二次确认，MVP 使用停用而非立即物理删除。
- 注册、建店、套餐变更、数据导出和停用门店均不得要求桌面端操作。

### 8.2 菜单管理

- 支持分类排序、菜品排序、价格、描述、图片和售罄状态。
- 支持必选/可选规格组，例如杯型、辣度或加料。
- 金额以整数 VND 保存和展示，不使用浮点数计算。
- 菜单修改先保存草稿，点击发布后对顾客生效。
- 已下单菜品保存名称、价格和规格快照，后续改菜单不改变历史订单。
- 所有编辑任务支持 360px 宽屏、软键盘和触摸操作；排序必须提供“上移/下移”等非拖拽备选操作。
- Free 手工建菜单必须提供“保存并继续新增”、复制菜品、记住上次分类/规格、数字键盘价格输入和批量上下架，不能故意把手工路径做得难用来逼迫升级。
- 手机拍照或上传后可以离开页面，AI 草稿完成时在站内提示，已安装 PWA 且授权后可收到通知。

### 8.2.1 AI 菜单助手

- 仅 Pro 支持“菜单图片/PDF → 结构化草稿”和权益范围内的多语言翻译草稿；Free API 必须返回明确的权益错误，不能仅在 UI 隐藏入口。
- 输出必须映射到分类、菜品、价格、规格和 locale 字段，不能只生成一段不可编辑文本。
- 每条 AI 内容保存来源、生成时间、模型/提示版本和审核状态。
- AI 结果默认状态为 `machine_draft`，店主确认后才变为 `reviewed`；只有已审核内容可发布。
- 价格、币种和规格选择规则必须由店主逐项确认；低置信度价格不得批量默认通过。
- AI 失败不能阻塞手工建菜单，且必须保留已上传素材和已完成草稿。
- 不将订单备注、顾客行为或付款记录发送给 AI 模型；菜单素材只用于本次处理，除非店主另行同意用于改进。

### 8.3 多语言

- 门店设置一种基础菜单语言。
- 每个分类、菜品和规格可以按目标语言填写翻译。
- 免费版只能发布基础语言；Pro 最多发布五种语言。
- 缺少翻译时回退到基础语言，并在后台明确提示缺失字段。
- 系统界面语言与菜单语言分离；顾客和员工界面可本地化，不消耗门店菜单语言额度。

### 8.4 桌台、取餐点与二维码

- 店主可创建、重命名、停用桌台。
- 店主可创建、重命名、停用柜台/门口取餐点；一张取餐码可被多位顾客同时使用。
- 每个桌台二维码包含不可猜测或可验证的令牌。
- 每个取餐点同样使用不可猜的独立 token，不与桌台 token 混用。
- 店主可下载单张二维码和适合 A4 批量打印的 PDF。
- 令牌泄露或被滥用时可重新生成，旧二维码立即失效。

### 8.5 顾客菜单与下单

- 首屏明确显示门店和桌号或“到店取餐”，防止扫错二维码。
- 顾客无需账号即可浏览和下单。
- 提交订单前显示完整金额和选项。
- 订单提交具备幂等性，弱网重试不会重复下单。
- 下单成功后展示稳定订单号。
- 外带订单额外展示门店当日唯一、易读易叫的取餐号；取餐号本身不能查看订单明细。
- 服务端拒绝已停用桌台、已下架菜品、非法价格和无效规格组合。
- 服务端同样拒绝已停用取餐点；堂食订单必须关联桌台，外带订单必须关联取餐点或已认证的代客下单员工。
- 门店可一键暂停/恢复扫码下单；暂停时顾客仍可查看菜单，但不能提交新订单或服务请求。
- 每桌的待处理订单数、服务请求和短时提交频率都有服务端上限；多次被取消或超限后进入冷却时间。
- 桌码被拍照外传时，店主可轮换 token 使旧码立即失效；防滥用不依赖定位或“同一 Wi-Fi”，以免阻断正常顾客。

### 8.6 员工工作台

- 默认按新订单优先展示，并可按桌台查看。
- 取餐/混合门店有独立取餐队列，按“新订单、制作中、可取餐”分组，卡片首要信息是大号取餐号和等待时间。
- 员工可为不扫码的现场顾客代建外带订单，与顾客自助订单使用同一取餐队列和状态机。
- “可取餐”和“再次叫号”动作显示全屏或大字取餐号，由员工口头叫号；MVP 不依赖扬声器、大屏或顾客 Push。
- 新订单有声音、震动（设备支持时）和明显视觉提示。
- 员工端首次启用必须引导安装 PWA、授权通知并完成一次测试通知。
- PWA 在后台或未打开时，通过 Web Push 显示新订单系统通知；点击通知直接打开对应订单。
- Push 是唤醒员工的提醒，不是订单数据源；打开应用后始终从服务端读取最新订单。
- 通知被拒绝、订阅失效或设备不支持时，工作台持续显示高优先级告警和修复指引。
- 状态修改必须在所有终端同步。
- 工作台同时显示新订单和服务请求；请求按“未响应 → 已响应 → 已完成”流转，并同步回顾客页面。
- 每次关键操作保存操作者、时间和前后状态。
- WebSocket 断开时显示离线提示并自动重连；恢复后拉取完整最新状态。

### 8.7 终端额度

- Free 同一门店最多一个活跃员工终端，Pro 最多五个。
- 活跃额度由服务端租约决定，不能只依赖浏览器本地状态。
- 终端异常断线后，租约应在合理超时内释放。
- 店主可以查看、命名和停用已配对终端。
- 店主后台配置页面不计入终端额度，但不能绕过限制执行订单操作。

### 8.8 结账记录

- 桌台账单聚合当前用餐批次的有效订单。
- 外带订单按单笔记录付款，不建立 table session，不与其他顾客订单合并。
- 默认在外带订单余额归零后才标记“已取餐”；如门店允许先取后付，员工端必须明示未付余额并记录例外。
- 支持记录一次或多次付款，以支持分次或分人结账。
- 付款修改通过冲正记录完成，不直接覆盖或删除原记录。
- 只有余额为零时才能正常关闭桌台；强制关闭必须填写原因。
- 页面明确提示“款项由餐厅直接收取，TaoMenu 不处理付款”。

### 8.9 订阅权益

- 权益检查在服务端完成，客户端显示不能作为授权依据。
- 套餐降级后不删除翻译或终端，只阻止超额语言发布并限制新的终端租约。
- 订阅接口与餐厅订单、付款记录完全隔离。
- MVP 可以由管理员手工授予 Pro；自动订阅计费在试点后接入。
- `AI 菜单导入`、`AI 翻译`、`语音识别/指令` 是独立的服务端布尔权益；降级后保留已审核并发布的数据，但不能创建新的 AI 或 STT 任务。

### 8.10 Pro 越南语语音助手

- PWA 只在用户主动按住或点击开始后申请麦克风权限并录音，不支持后台或持续监听。
- STT 结果必须经过结构化指令 schema、服务端权限和当前业务状态三层校验。
- 涉及价格、付款、取消、删除、发布或关桌的操作必须再次点击确认。
- 动态向 STT 提供当前门店的菜名、规格、桌号和越南语常用词，提高专有词识别率。
- 保存转写、解析结果、最终决定和操作者用于审计；原始音频按短保留期自动删除。
- 弱网或识别失败时不得猜测执行，用户始终可以返回手工操作。

## 9. 体验与非功能要求

### 9.1 性能

- 越南普通 4G 网络下，已优化菜单首屏目标在 2.5 秒内可交互。
- 顾客下单接口目标 P95 小于 1 秒，不含用户网络时间。
- 员工端新订单正常情况下在 2 秒内可见。
- 菜品图片使用响应式尺寸和压缩格式，不阻塞菜单文字加载。

### 9.2 可用性

- 顾客端优先适配手机窄屏和单手操作。
- 顾客订单页进入后台时停止订单状态轮询；通过 `visibilitychange`、`pageshow` 或用户主动下拉刷新在回到页面时同步最新状态。
- 顾客端不要求安装 PWA，不为取餐叫号申请通知权限。
- 店主后台是 mobile-first 产品，而不是桌面后台的缩小版；从注册到取消订阅的全部流程必须在手机完成。
- 主操作使用底部可达区域和至少 44×44 CSS px 的触控目标；不依赖 hover、右键、多列宽表格或精确拖拽。
- 表单支持自动保存草稿、离开恢复、明确错误定位和软键盘遮挡处理；破坏性操作提供撤销或二次确认。
- 二维码、菜单预览和报表使用系统分享能力；即使系统不支持 Web Share，也能下载和复制链接。
- 员工端按钮适合快速点击，关键状态不能只依赖颜色区分。
- 新订单声音必须由员工主动开启，以符合浏览器自动播放限制。
- 视觉、色彩、字号、间距、触摸目标和三端布局遵循 [TaoMenu 设计系统](./DESIGN_SYSTEM.md)；产品状态不得只用颜色表达。
- iOS/iPadOS 员工必须把 PWA 添加到主屏幕后，才能申请 Web Push 权限。
- 通知权限只能在员工明确点击“开启通知”后申请，不能在页面加载时突兀弹窗。
- 营业准备页显示每台终端的安装、通知权限、Push 订阅、WebSocket 和最后同步状态。
- Push 不承诺自定义警报声、绕过系统勿扰模式或绝对送达；营业时建议至少一台终端保持前台并开启声音。
- PWA 可安装到主屏幕；断网时员工端只显示最后同步数据和明确的只读状态。

### 9.3 隐私

- 默认不收集顾客姓名、手机号、邮箱和精确位置。
- 不将顾客数据用于跨店画像或广告追踪。
- 订单备注可能包含个人信息，应设置保留期限并允许门店删除。
- 员工和店主操作保留必要审计信息。

### 9.4 可访问性与本地化

- 关键顾客流程达到 WCAG 2.2 AA 的基本要求。
- MVP 系统界面至少提供越南语和英语；中文用于营销和运营支持，可随试点加入。
- 日期、数字和金额按门店地区格式展示。

## 10. 数据与指标

### 10.1 北极星指标

每周成功处理至少一笔真实订单的活跃门店数。

### 10.2 激活漏斗

1. 完成注册。
2. 创建门店。
3. 手工录入菜单；Pro 也可拍摄/上传菜单。
4. 审核并发布菜单。
5. 创建桌台码或取餐码。
6. 配对员工终端。
7. 收到第一笔真实订单。

### 10.3 产品指标

- 周活跃门店和 4 周留存。
- 每活跃门店每周订单数。
- 从扫码到成功下单的转化率和耗时。
- 订单取消率和重复提交拦截数。
- 外带订单占比、从接单到可取餐的耗时、可取后到已取餐的耗时和再次叫号率。
- 顾客切回订单页后的状态刷新成功率；不记录顾客在其他应用中的行为。
- 呼叫服务员/请求结账的使用率、首次响应时间和重复请求拦截数。
- 桌码滥用拦截、冷却触发和门店暂停扫码下单次数。
- 员工终端实时连接成功率和重连率。
- 免费门店触发终端上限、多语言上限的次数。
- Free 到 Pro 转化率和付费门店流失率。
- Free 手工录入和 Pro 拍照导入分别从首个动作到发布的耗时。
- AI 字段接受率、价格修正率、语音关键字段错误率、确认取消率和 AI/STT 任务失败率。
- 自然搜索 impression → 注册 → 发布首份菜单的关键词级漏斗。

指标事件不记录菜品备注、顾客身份或完整 IP。

## 11. 上线阶段

### 阶段 A：可用原型

- 单门店、单语言菜单。
- 手机后台和完整手工菜单编辑。
- 桌台码、公共取餐码和顾客下单。
- 外带取餐号、可取餐队列、员工口头叫号和已取餐闭环。
- 呼叫服务员、请求结账和员工确认。
- 单员工终端接单。
- PWA 安装、Web Push 订阅和新订单测试通知。
- 现金/转账人工确认和关闭桌台。
- 外带订单的单笔现金/转账人工记录。

### 阶段 B：封闭试点

- 邀请 5～10 家真实门店。
- 多终端实时同步和终端额度。
- 多语言菜单。
- Pro 拍照/PDF 建菜单、AI 翻译草稿和越南语语音输入/受控指令。
- PWA 安装、弱网恢复和操作审计。
- 管理员手工授予 Pro。

### 阶段 C：公开测试

- 自助注册和完整新手引导。
- SaaS 订阅计费。
- 越南语营销站、帮助中心和隐私/服务条款。
- 按关键词研究发布高意图越南语落地页、结构化数据和 sitemap。
- 基础运营指标和错误监控。

## 12. 关键风险与验证

| 风险 | 首要验证方式 |
|---|---|
| 门店认为纸笔已经足够 | 观察高峰期流程，衡量每桌点单和结账等待时间 |
| 顾客不愿扫码 | 统计扫码后菜单打开率，优化桌卡文案和首屏速度 |
| 单终端免费版已足够，缺少付费动力 | 记录终端上限触发和高峰期并发需求 |
| 多语言不是高频需求 | 对游客区和本地社区门店分组验证 |
| 网络不稳定造成漏单 | 前台 WebSocket、后台 Web Push、自动重连、全量重同步和轮询共同兜底 |
| 员工拒绝通知权限或 iOS 未安装 PWA | 首次配对强制完成能力检测和测试通知，营业准备页持续提示 |
| Push 被系统延迟、静音或丢弃 | 不以 Push 作为订单事实来源；至少一台营业终端保持前台声音提醒，并监控订单首次查看耗时 |
| 手机录入菜单太慢导致店主放弃 | Free 优化分步手工录入；Pro 把拍照导入作为升级后的主路径，并分别跟踪两条路径的耗时和放弃点 |
| 桌码被拍照外传后恶意下单或轰炸请求 | 服务端频率/待处理上限、同类请求合并、冷却、一键暂停和 token 轮换共同防护 |
| 无座店顾客切到其他 App 后看不到取餐进度 | 不假设页面常驻；以员工口头叫号为主，顾客切回/pageshow/下拉时立即刷新服务端状态 |
| 取餐号重复或不易口头辨认 | 按门店当地营业日生成短号码，数据库唯一约束和并发测试保证不重号；字母前缀避免与桌号混淆 |
| 登录验证码邮件延迟导致注册流失 | Google 作为快捷入口，邮箱 OTP 作为无 Google 账号的备选和恢复通道 |
| AI 识别错价或错误翻译 | AI 只生成草稿；价格低置信度强提醒，发布前由店主确认并保留来源记录 |
| 精确 QR 点餐词搜索量太低 | 同时覆盖餐厅管理/点单宽词和手机、多语言问题词，用 Search Console 验证后再决定广告或地推 |
| 多租户被误解为交易平台 | 坚持业务边界，并在正式商业化前复核产品、合同和页面表述 |

## 13. MVP 完成定义

同时满足以下条件才视为 MVP 可进入封闭试点：

- 店主可无人工介入创建门店、菜单和桌码。
- 无座门店不创建虚拟桌号也能完成建店、生成取餐码和测试订单。
- 上述店主流程、终端管理、套餐变更和数据导出均可在 360px 宽的手机上完成。
- Free 店主可在手机上手工创建完整菜单；Pro 店主可从菜单照片生成结构化草稿。
- Pro 越南语语音写操作必须经过确认；未经确认的 AI 内容或语音指令绝不改变业务数据。
- 两台顾客手机可向同一桌台追加订单且不串单。
- 一个员工终端可以完成接受、上菜、记录付款和关闭桌台。
- 一个员工终端可以完成外带订单的接受、可取餐、再次叫号、已取餐和单笔付款记录。
- 顾客将页面切到后台后不持续轮询；切回、页面恢复或下拉刷新时能看到最新取餐状态。
- 同一门店营业日内并发创建外带订单不会产生重复取餐号。
- 顾客的“呼叫服务员/请求结账”能到达员工端，员工确认和完成状态能回到顾客页面。
- 恶意重复订单、重复服务请求、暂停营业和桌码 token 轮换均有自动化测试覆盖。
- iOS 和 Android 真机在 PWA 后台及锁屏状态下通过测试订单收到系统通知。
- Push 失败时，前台 WebSocket 和轮询仍能发现订单，恢复连接后不会漏单或重复下单。
- Pro 门店五个终端并发操作时状态最终一致，冲突有明确结果。
- Free 门店无法绕过一个活跃员工终端限制。
- 无效桌码、重复下单和越权租户访问均被自动化测试覆盖。
- TaoMenu 的任何账户都不能收到或控制顾客支付给餐厅的餐费。

## 14. 搜索与 AI 获客要求

关键词研究的完整数据、页面映射和验证计划见 [越南关键词研究](./KEYWORD_RESEARCH.md)。产品层面的硬要求是：

- 越南语首页同时表达 `phần mềm order nhà hàng`、`menu QR` 和“只需手机”，不把品牌名当作主要自然搜索入口。
- 首批建立面向“餐厅点单软件、QR 菜单、手机点单、免费试用、多语言菜单、法棍/外带店取餐叫号”的独立高意图页面。
- 营销与帮助页面可索引；店主后台、员工终端和桌码顾客菜单默认 `noindex`，不形成跨餐厅目录。
- 页面内容、价格、权益和限制使用结构化、可引用且有更新时间的表述，方便传统搜索和 AI 搜索理解。
- SEO/AEO 的成功标准不是排名本身，而是自然搜索带来的“发布首份菜单”激活数和后续真实订单门店数。
